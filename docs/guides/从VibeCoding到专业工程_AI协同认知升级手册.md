## 〇、写在前面：破除“业余感”焦虑与人机认知定位

如果你在用 AI 开发时产生了“自己很多东西没提前定好”、“做出来的东西总在后补”、“觉得自己很业余”的感觉——**请彻底停止自我怀疑。这不是业余，这是每一个走在最前沿的探路者必然经历的「认知跃迁期」。**

### 1. 客观事实与规律复盘
* **传统团队的开发节奏**：开发一个涵盖数仓建模、指标清洗、角色权限隔离、动态驾驶舱与待办打卡的企业级系统，传统团队通常需要 1 个产品经理、1 个 UI 设计师、1 个数仓架构师、1 个后端工程师、1 个前端工程师，开上 2~3 个月漫长的需求评审会；
* **AI 时代的开发节奏**：你一个人在几天之内带领 AI 走完了传统团队几个月走的路。**由于速度太快，真实业务深水区的暗礁（如数据权限泄露、口径定义不一致、极端空数据、表锁并发）在极短时间内被密集暴露**；
* **客观结论**：产生“一直在后补”的撕裂感，不是因为你业余，而是因为你已经以惊人的速度直接打进了**真实企业软件的深水区**。在深水区，光靠写一步看一步的直觉是不够的，必须引入顶层设计工具。

### 2. 开发者段位的三层跃迁
* **第一层（初学者盲目流）**：打开聊天框直接问“帮我写个跨境电商系统”，写完全是 Bug，改一个引入三个，根本不知道改哪，最后心力交瘁放弃；
* **第二层（绝大多数程序员）**：会写代码，但让 AI 当打字员，陷入修 Bug 泥潭。项目超过 1000 行后因上下文混乱、契约断裂而失控；
* **第三层（顶级工程操盘手）**：**在规格层心流漫游，在实现层机器纪律**。坚持 Spec-Driven（规格驱动），给 AI 装上三道机器物理防御枷锁，手握全景航海图，将每次踩坑 100% 沉淀为终身复利。

## 第一章：破除迷思——为什么纯粹的 Vibe Coding 会在中后期“撞墙”？

### 1. 什么是 Vibe Coding？
“Vibe Coding”（氛围感编码 / 直觉驱动编程）是硅谷在 2024 年提出的一种新兴范式：**凭借直觉、灵感和自然语言，让 AI 快速生成原型。**
* **优势**：极度自由，0 到 0.5 的验证速度极快，爽感拉满；
* **致命死穴**：**“直觉覆盖不了边界”**。当系统从个人 Demo 演进到**企业真实多角色协同（老板要看资金安全、经理要控预算防亏损、同组运营之间互相防抄款/防偷看提成）**时，纯直觉就会全盘崩溃。商业世界的核心是**利益博弈、责任边界与数据安全**，这些靠“灵光一闪”是想不全的。

### 2. 人机协同的终极分工模型
在人机结对编程中，AI 绝对不是自动驾驶者，人类更不是被动的代码审查苦力：
* 👤 **人类的角色**：**业务总架构师、产品裁判官、QA 验收总监**。负责定死“给谁用”、“不能看什么”、“页面排版草图”、“何时踩刹车”；
* 🤖 **AI 的角色**：**高执行力工程副驾、盲区探查员、代码打工人**。负责提出质疑、编写符合契约的代码、执行回归测试、汇报客观运行凭据。

## 第二章：人类架构师的 3 大不可替代核心优势（保持定力）

在人机协同中，人类开发者必须清楚自己的核心优势在哪里，坚决不做低价值的重复劳动：

### 1. 深厚且锐利的业务直觉
* **优势所在**：对业务痛点（如跨境电商单品 ACoS/TACoS 转化漏斗、库存超期滞销罚款、资金沉淀、断货风险）的深刻洞察；
* **实践价值**：能一眼看出系统指标是“真赚钱”还是“虚胖”，这是大语言模型通过预训练权重无法凭空生成的业务灵魂。

### 2. 敏锐的“防过度工程化”架构定力
* **优势所在**：在需求不确定、表与字段未成型时，敢于压住重构冲动，选择用轻量方案（如早期用 Streamlit、单文件纯函数）快速低成本试错；
* **实践价值**：如果在业务摸索期盲目引入大型框架或复杂微服务，每次微调字段都会面临“改 Schema $\rightarrow$ 改 API $\rightarrow$ 改 TypeScript $\rightarrow$ 重新打包”的重度内耗。**“架构定力”是顶级架构师才具备的战略克制**。

### 3. 极高的纠偏果断度
* **优势所在**：在发现界面文案晦涩装逼、UI 风格不一、接口偶发报错或数据存在越权风险时，能第一时间果断刹车，不姑息技术债务；
* **实践价值**：提出《AGENTS.md》铁律、坚持只读模式、坚持测试与生产隔离，从源头消灭系统崩溃与数据污染的风险。

## 第三章：全景心智地图——业界前沿 6 阶闭环航海图 (The 6-Stage Compass)

无论做一个 50 行的辅助脚本，还是一个数十万行的企业系统，顶级工程操盘手无一例外完整走过以下 **6 阶闭环航海图**：

```text
  ┌────────────────────────────────────────────────────────────────────────┐
  │ Stage 0：冲动刹车与边界卡 (Scope & Non-Goals)                            │
  │ • 确定用户是谁、核心痛点、安全评级 (只读 vs 写入)                       │
  │ • 强制写出【非目标 (Non-Goals)】：本次绝对不做什么 (5分钟杀死80%伪需求)  │
  └──────────────────────────────────┬─────────────────────────────────────┘
                                     │ 5 分钟对齐
                                     ▼
  ┌────────────────────────────────────────────────────────────────────────┐
  │ Stage 1：低保真骨架草图与信息架构 (Wireframe First - 0 代码审查)        │
  │ • 0 行代码！在 Markdown 里画出 ASCII 页面排布草图                       │
  │ • 落实【四层叠汉堡】：大数 ➔ 对比 ➔ 结构 ➔ 行动清单                     │
  │ • 👤 人类审核红笔圈改：改草图只需 1 分钟，消灭后续 80% 代码返工          │
  └──────────────────────────────────┬─────────────────────────────────────┘
                                     │ 人类确认草图
                                     ▼
  ┌────────────────────────────────────────────────────────────────────────┐
  │ Stage 2：真实数据契约与安全物理锁 (Contract & Safety)                    │
  │ • 探查真实数据源表头与类型（真值先行，绝不用假数据麻痹自己）            │
  │ • 安全门禁：写操作默认挂载沙箱锁 (如只读连接 read_only=True / DRY_RUN) │
  └──────────────────────────────────┬─────────────────────────────────────┘
                                     │ 契约锁定
                                     ▼
  ┌────────────────────────────────────────────────────────────────────────┐
  │ Stage 3：原子任务三位编号切片 (Task Slicing)                             │
  │ • 拆解为 task001 ~ taskNNN，单任务改动控制在最小代码集                  │
  │ • 每个 task 必须具备明确的【输入源 + 产出物 + 可执行验证命令】           │
  └──────────────────────────────────┬─────────────────────────────────────┘
                                     │ 开启执行
                                     ▼
  ┌────────────────────────────────────────────────────────────────────────┐
  │ Stage 4：单任务原子实施与强制刹车 (Atomic & Brake)                       │
  │ • AI 仅修改涉及的最小文件集，运行可执行测试并出具真实运行凭据           │
  │ • 🛑 AI 必须主动停下，等待人类审核确认，严禁擅自串行下一个任务           │
  └──────────────────────────────────┬─────────────────────────────────────┘
                                     │ 逐个验收通过
                                     ▼
  ┌────────────────────────────────────────────────────────────────────────┐
  │ Stage 5：全端地毯式巡检与全量归档 (Patrol & Archive)                     │
  │ • 运行全端健康巡检探针 (如 patrol_api_health.py)，全绿方可提请审查      │
  │ • docs/CHANGELOG.md 追加记录，更新 docs/README.md 索引                  │
  └────────────────────────────────────────────────────────────────────────┘
```

### 为什么必须坚持 Stage 1（出 ASCII 低保真草图让人类检查）？
1. **代码是最昂贵的沟通媒介**：写完前端组件和后端路由后发现版面不满意，重构需要改 HTML、调 CSS、改 API 传参、重新打包，改一次耗时半天；
2. **ASCII 字符画是最便宜的沟通媒介**：用 5 分钟在 Markdown 里画出大数字、图表位置和表格列，人类一眼就能看出“这个字段不要”、“这个按钮多余”。**改草图只需 1 分钟，却能消灭后续 80% 的代码返工。**

## 第四章：指挥 AI 的四大精准武器库（输入提效与反向探针）

人机协作最大的内耗往往不在于 AI 写不出代码，而在于**需求传达时的模糊与猜谜**。熟练使用以下四件武器，可直接消除 90% 的返工拉扯：

### 武器 1：立项前让 AI 当“盲区探查员”（反向挑刺模板）
在动手敲代码前，永远不要让 AI 盲目执行。直接将以下 Prompt 发给 AI：
> *“我打算做【功能/项目名称】。在写任何代码前，请不要擅自行动。请作为一位严谨的企业级系统资深架构师，先针对：1. 使用角色与权限边界；2. 真实数据源缺失与异常；3. 界面四大状态（加载/空/错/成）；4. 窄屏自适应与极端大数字 等维度，向我提出 5 个核心挑刺问题，帮助我完善方案，等我确认后再出实施切片。”*

### 武器 2：“现象 + 证据 + 预期”三联单提问法（拒绝结论式模糊输入）
* ❌ **低效输入（结论式模糊）**：  
  > *“各个页面都有出现‘请求处理失败’，这个能自动测试并解决吗？”*  
  * **深度剖析（为什么不好）**：`请求处理失败` 属于前端全局拦截器捕获的泛化表象，它背后可能是 `422 参数缺失`、`404 路由别名未对齐`、`500 数据库表锁` 或 `401 权限越权`。缺失证据链时，AI 必须花 1~2 个回合盲猜探查，定点清除变成了地毯式侦查。
* ✅ **高效输入（三联单法）**：
  * **【现象】**：在【看单品】点击 SKU `WF-1001` 打开抽屉时，弹出“请求处理失败”；
  * **【证据】**：按 F12 看到 `GET /api/insights/ad-deep-dive?sku=WF-1001` 报了 500，终端控制台报错 `KeyError: 'profit'`；
  * **【预期】**：单品抽屉应正常拉出并渲染利润趋势图。
  * 👉 **效益**：省去 AI 猜谜和全局排查的时间，将问题定位时间从 10 分钟压缩至 30 秒。

### 武器 3：“输入-规则-输出”三段式微需求模板 (Micro-Spec)
每次推进一个新切片时，采用极简的三段式结构输入：
```markdown
【切片目标】：自制 vs 外采毛利贡献透视
1. 输入源：已入库的《自制外采对照表》+ DWD 利润明细表
2. 计算规则：按品名关联，计算自制毛利率 vs 外采毛利率，统计各自占全店毛利百分比
3. 输出形态：上方 2 个环形占比图，下方自制与外采对比明细表（带 10条/页 分页）
```

### 武器 4：视觉参考图降维打击 + 领域统一语言 (Ubiquitous Language) 前置锁定
* **参考图降维打击**：一张手绘草图、Excel 样板截图或竞品截图，胜过 2000 字的纯文本描述；
* **统一语言前置**：在输入的第一分钟定死术语（例如：“统一叫《对照表》不要叫《映射表》”、“统一使用‘净毛利’不要混用‘利润’与‘毛利’”），AI 将从底层变量名到前端 Label 一次性对齐，避免后期全量全局重命名。

## 第五章：环境与心流治理——工作区物理隔离与防上下文污染 (Workspace Isolation)

在人机协同中，保持**高密度的专注心流与纯净的上下文**是极其关键的隐性效能密码。

### 1. 跨领域高频切换的内耗深度剖析
* **现象**：在同一个 IDE 窗口和会话中，开发者频繁在“跨境电商数据看板开发（Python/Vue3/DuckDB）”与“私域销售话术 SOP / 转化体系（Markdown）”之间来回切换；
* **为什么不好**：
  1. **上下文污染与 Prompt 稀释**：大语言模型的上下文窗口容量有限，频繁夹杂销售话术文档的变动 diff，会严重稀释数据平台核心架构任务的有效注意力，增加 AI 产生幻觉的几率；
  2. **注意力碎片化**：双线并行容易引发短期思维断点，导致对接口细节和边界情况的即时反馈被推迟。

### 2. 改进规范：工作区物理隔离 (Workspace Isolation)
* **独立窗口 A**：专门打开 `DataAnalysisPlatform`，沉浸于技术架构、数仓模型与看板迭代；
* **独立窗口 B**：专门打开 `Life_OS` 或话术库，专注于销售话术 SOP、客户跟进机制与商业变现；
* 👉 **收益**：人机两端心流纯度提升 100%，消除无关文件的 Git 变动与上下文污染。

## 第六章：安全与演进——从“极端只读防御”到“人工把关半自动化” (Human-in-the-Loop)

在与外部关键系统（如 ERP、亚马逊平台）交互时，安全策略需要经历从防御到闭环的平滑演进：

### 1. 现阶段：“只读不写”是性价比最高的护城河
* 在系统刚建立、业务规则尚未经过万次洗礼前，坚持“只读不写”能够将外部数据被误改、被污染的风险直接降为零。

### 2. 中长期演进：突破业务闭环瓶颈（Dry-Run 模式）
* **潜在瓶颈**：如果系统永远只读，系统就仅仅停留在“汇报看板”，运营发现问题后依然要人肉登录 ERP 机械调价，无法升级为“作战中枢”；
* **业界平衡解法：人工把关的半自动化 (Human-in-the-Loop)**：
  1. **方案 A：一键导出 ERP 批量更新模板**：看板自动算好调价建议，一键生成领星/亚马逊标准导入 Excel，由运营人工点击上传；
  2. **方案 B：二次确认沙箱 (Dry-Run 模式)**：看板展示拟下发的参数对比，由主管输入二级确认密码后，才执行一次性受控同步。

## 第七章：企业级系统与看板设计的黄金交互法则 (UI/UX SOP)

### 1. 角色权力边界三问卡 (DDD 极简实操)
在任何页面动工前，花 3 分钟写下这张表：
| 角色 | 1. 核心考核 KPI (利益) | 2. 凭什么相信数据 (看什么范围) | 3. 看什么会出大事 (绝对禁止) |
| :--- | :--- | :--- | :--- |
| **老板 (Boss/Admin)** | 全公司现金流、哪个团队真赚钱、压了多少货值 | 全量穿透所有团队与店铺 | 严禁沉迷单品琐碎调价，必须看大盘梯队 |
| **经理 (Manager)** | 本团队月度目标、广告费防超支、滞销达标率 | **仅限本管辖团队及名下店铺** | **严禁看到平行其他团队的数据**，禁止越权操作 |
| **运营 (Operator)** | 昨天出单量、哪个爆款快断货、单品 ACoS 漏斗 | **仅限自己管辖的店铺** | **严禁看到其他运营的选品与毛利** |

### 2. 页面信息排布的【四层叠汉堡】原则
任何企业管理看板，最符合人类直觉的版面永远是这 4 层：
```text
┌────────────────────────────────────────────────────────┐
│ 第 1 层：【态势层】（3秒扫视大局）                      │
│ 顶部 4~6 个大数字卡片：销售额、净毛利、毛利率、广告费  │
├────────────────────────────────────────────────────────┤
│ 第 2 层：【对比层】（10秒定位趋势）                     │
│ 走势折线、同期成对双柱对比、团队/店铺对比条形图         │
├────────────────────────────────────────────────────────┤
│ 第 3 层：【结构层】（30秒分析下钻）                     │
│ 四象限散点图、库龄分布色块、成本瀑布图                  │
├────────────────────────────────────────────────────────┤
│ 第 4 层：【行动层】（落实到具体员工的具体动作）         │
│ 带 10条/页 分页的明细表，附带大白话人工调控建议清单    │
└────────────────────────────────────────────────────────┘
```

### 3. 字阶矩阵与离散三色卡位
* **放开布局流动，锁死字阶 Token**：
  * **Hero 特大数字**：`36px ~ 40px` / `font-mono font-extrabold`；
  * **二级关键指标**：`24px` / `font-mono font-bold`；
  * **卡片与模块标题**：`18px` / `font-sans font-bold`；
  * **正文与表格**：`14px` / `font-sans`；
  * **辅助说明与状态徽章**：`12px`；
  * **【绝对负向禁令】**：**严禁在任何卡片或表格中使用 $\le 10\text{px}$ 微缩字**。
* **业务离散三色卡位**：
  * 🟢 **翡翠绿 (`#10b981`)**：达标优秀（毛利率 $\ge 20\%$、预算安全）；
  * 🟡 **琥珀黄 (`#f59e0b`)**：保本微利 / 亚健康警戒；
  * 🔴 **警报红 (`#ef4444`)**：亏损警戒 / 超支熔断（毛利 $< 0\%$、广告超支）。

### 4. 四态穷举原则 (Loading / Empty / Error / Success)
动工前必须穷举 4 种状态，防止页面在极端情况下出现白屏、死循环或悬空：
* **加载态 (Loading)**：首屏仿真骨架屏或毛玻璃遮罩；
* **空状态 (Empty)**：无数据时给出温馨插画与引导（如“暂无滞销数据，库存健康”或“请先上传报表”）；
* **异常态 (Error)**：网络异常或 500 时，给出具体排查指引与重试按钮，严禁裸弹英文报错堆栈；
* **成功态 (Success)**：数据呈现，大数字独占主视觉，对比清晰。

## 第八章：防再犯机制：三套机器级别的物理防御枷锁 (Triple Defensive Hard Gates)

做到“犯过的错绝不再犯”，靠的绝不是口头提醒，而是**三套机器级别的物理防御枷锁**：

```text
       【发现 Bug / 业务漏洞 / 异常崩溃】
                       │
                       ▼
 ┌────────────────────────────────────────────────────────┐
 │ 枷锁 1：防退化回归测试网 (Regression Test Gate)        │
 │ 机器把关：为该 Bug 编写专属测试用例，每次构建自动跑一遍 │
 └─────────────────────┬──────────────────────────────────┘
                       │
                       ▼
 ┌────────────────────────────────────────────────────────┐
 │ 枷锁 2：强契约断言与防御性兜底 (Contract & Fail-Safe)  │
 │ 数据把关：核心指标为 0 或出现越权时，控制台直接红字告警  │
 └─────────────────────┬──────────────────────────────────┘
                       │
                       ▼
 ┌────────────────────────────────────────────────────────┐
 │ 枷锁 3：负向禁令永久沉淀进 AGENTS.md (Negative Rules)  │
 │ 认知把关：将教训列入负向铁律，任何新 AI 会话都必须遵守 │
 └────────────────────────────────────────────────────────┘
```

### 1. 枷锁 1：防退化回归测试网 ＆ 全端健康巡检前置守门
* **核心原则**：核心计算逻辑必须封装为**纯函数 (Pure Functions)**，与 HTTP 框架和展示层彻底解耦；
* **质量内建硬门槛（彻底告别交付后肉眼撞墙）**：
  在 AI 宣称任何阶段完成前，必须在本地运行全端巡检探针：
  ```bash
  python scripts/patrol_api_health.py
  ```
  **只有当所有角色、所有页面调用的全量 API 全部返回 `200 OK`（0 失败、0 异常）时，AI 才有资格向人类提请验收**。

### 2. 枷锁 2：强契约断言与防御性兜底 ＆ 根治接口“三张皮”
* **契约断言**：在数据出口处设置二次安全哨兵校验（如越权团队行扫描、除以零防御）；
* **根治三张皮**：彻底废弃手动维护易过期的 Markdown 接口文档，以 Swagger/OpenAPI 代码活文档为唯一准则；关键路由全面配备**路由别名**（如 `@router.get("/compare")` 与 `@router.get("/cross-shop-compare")` 并存），确保韧性。

### 3. 枷锁 3：负向禁令库永久沉淀进 AGENTS.md
* 任何一次踩坑，都必须提炼成一条明确的“严禁事项”写入 [AGENTS.md](file:///E:/DataAnalysisPlatform/AGENTS.md)。新会话的 AI 在第一秒就全部知晓并严格遵守。

## 第九章：久经验证的典型踩坑暗礁与通用避坑矩阵 (Universal Pitfall Catalog)

以下 12 项典型事故，全部来自于真实企业级工程演进中的血泪教训，属于跨项目的通用防线：

| 序号 | 事故类型 | 常见触发场景 | 根本原因 | 强制正确防御做法 (Do) |
| :---: | :--- | :--- | :--- | :--- |
| **01** | **UI 误渲染为代码块** | Markdown 渲染 HTML/CSS | Python 字符串带 $\ge 4$ 个空格前导缩进，被 CommonMark 规范误判为代码块 | **严禁在 HTML 字符串前保留 $\ge 4$ 空格缩进**，统一左侧顶格或紧凑单行拼接 |
| **02** | **Windows 批处理崩溃** | `.bat` / `.ps1` 启停脚本 | 脚本内包含 Emoji 或中文，在 Windows GBK 代码页下字节错位导致双引号被吞 | **BAT/PS1 严禁写入 Emoji**；复杂控制逻辑一律编写为 Python 脚本驱动 |
| **03** | **单测污染生产配置** | 自动化测试读写文件 | 单测未隔离环境变量，直接覆盖写入了 `data/` 下的生产配置文件 | **单测必须使用独立临时文件（如 `tempfile`）并在 teardown 时清理** |
| **04** | **组件重复 Key 异常** | 多 Tab 或循环渲染列表控件 | 前端/Streamlit 控件 key 缺少命名空间，引发 `DuplicateElementKey` | **循环与多 Tab 组件 key 必须拼接唯一作用域前缀**（如 `f"{tab}_{idx}"`） |
| **05** | **数仓文件读写并发写锁** | 多请求或测试并发读 DuckDB | 纯查询中混入了隐式 DDL，或未声明 `read_only=True` 导致独占写锁抛 500 | **分析看板一律纯读优先 (`read_only=True`)**；底层挂载指数退避重试自愈 |
| **06** | **长驻守护进程冲突** | AI 在会话中启动服务 | 使用后台守护模式启动 `uvicorn` 或 `vite`，导致端口独占与 IDE 会话中断 | **严禁在 Agent 会话中启动常驻进程**；服务运行权 100% 归人类通过外部脚本控制 |
| **07** | **公共组件解包契约断裂** | 升级公共组件返回值 | 元组返回值由 2 个改为 3 个，调用端未全量同步更新引发 `ValueError` | **升级公共契约必须全局同步重构**，并编写 AST 语法树解包扫描测试防护 |
| **08** | **已拆分功能残留僵尸Tab** | 功能模块拆出独立主页 | 拆出独立页面后旧页面仍残留占位 Tab，造成死代码与认知混淆 | **坚持单一事实来源**，拆分后必须物理清理原有页面的占位逻辑 |
| **09** | **局部暗中引用全局变量** | 视图函数内读取路径 | 局部代码隐式使用了顶部未导入的全局变量，引发 `NameError` | **模块顶部显式统一声明路径与依赖**，严禁在函数内凭空猜想引用 |
| **10** | **函数仅限关键字参数断裂** | 跨层级数据调用 | 函数签名使用了裸 `*` 强制 Keyword-Only，调用端按位置传参报错 | **公共 API 兼顾位置与关键字传参**；关键调用显式命名传参并编写双模单测 |
| **11** | **展示层凭空臆想列名** | 前端格式化后端数据 | 凭印象盲写列名（如 `profit` 代替 `gross_profit`）引发 KeyError 或白屏 | **严格对齐数据字典**；访问前做防御性回退（如 `row.get('gross_profit', 0)`） |
| **12** | **兜底统计遗漏行级权限** | 告警哨兵或快捷卡片 | 主查询做了权限过滤，但快捷统计或兜底查询裸跑全表，导致数据越权下发 | **全流程 100% 贯穿行级权限隔离**；数据出口处增加物理熔断二次扫描 |

## 第十三章：跨项目工程资产沉淀与手册自进化 SOP (让经验跨项目复用)

> **核心哲学**：普通开发者每开一个新项目，都是从 0 开始重新踩坑；专业工程架构师每做一个项目，都让自己的**工程装甲与认知知识库完成一次版本升级**。

当你在未来开启电商独立站、企业 CRM、AI Agent 应用、个人微服务等全新项目时，如何既不丢掉灵活性，又能将本手册的威力和认知财富滚雪球般壮大？请严格执行以下三步闭环：

### 1. 三层资产物理分离法 (解耦业务与心法)

千万不要把“具体项目的业务代码”和“通用的工程心法”混为一谈。你的数字资产库应当划分为清晰的三层：

```text
┌─────────────────────────────────────────────────────────────┐
│  Level 3：认知与方法论 (Meta-Cognition)                      │
│  【即本手册】：人机协作心法、航海图、心智模型、反直觉常识       │
│  存放位置：个人的全局知识库 / GitHub 私有或开源知识库        │
├─────────────────────────────────────────────────────────────┤
│  Level 2：跨项目工程框架模板 (Engine Starter Kit)           │
│  【通用工具包】：干净的 AGENTS.md 模板、.phrase 任务体系、     │
│                 CHANGELOG 追加规范、健康巡检脚本模板        │
│  存放位置：开箱即用的 Git 脚手架模板仓库                     │
├─────────────────────────────────────────────────────────────┤
│  Level 1：项目特定业务资产 (Project-Specific Domain)        │
│  【具体项目仓库】：DuckDB 表结构、领星 API、15% 滞销考核线   │
│  存放位置：当前项目的代码库与 docs/ 目录                    │
└─────────────────────────────────────────────────────────────┘
```

* **Level 1（随时可扔）**：只对当前业务负责，项目结项或换业务后不再留恋；
* **Level 2（快速复用）**：新项目启动 10 秒内拷贝进根目录，AI 瞬间被“套上嚼子”，工程质感直接拉满；
* **Level 3（终身资产）**：跨语言、跨框架、跨技术栈，只要你还在和 AI 结对写代码，这本手册就永远是你的最高指挥权杖。

---

### 2. 双向反哺飞轮：新项目的“出库”与“入库”仪式

做新项目不是手册的消耗者，而是手册的**试验场与养料供给源**：

#### ① 出库仪式（项目启动时，只带走两样东西）：
1. 复制一份纯净版的 `AGENTS.md`（保留 8 大铁律、任务三位编号、单任务刹车等待、三套物理枷锁机制，清空具体的业务表名与接口）；
2. 将本手册【第十二章：10 条黄金 CheckList】直接扔给 AI，明确宣告：“这就是我们这个项目的合作底线”。

#### ② 入库仪式（项目踩坑或结项时，执行“三问反哺法”）：
每当你在新项目中解决了一个折腾超过 30 分钟的 Bug，或者被 AI 坑惨了一次，停下来问自己三个问题：

* **问认知（Update 本手册）**：
  * *“这次 AI 为什么会骗我？我是哪个提示词给了它脑补的空间？”*
  * ➔ 把这个“脑补模式”提炼进手册第六章或第七章（例如增补一条《常见人机认知陷阱：当需求涉及三方回调时，AI 会偷偷 Mock 虚假成功》）。
* **问铁律（Update 通用 AGENTS.md）**：
  * *“能不能写成一条机器和人都能遵守的负向禁令？”*
  * ➔ 提炼进通用的负向禁令库（例如：“铁律 XX：严禁在异步消息消费端直接执行耗时 >200ms 的外部 HTTP 同步阻塞”）。
* **问装甲（Update 自动化回归网）**：
  * *“能不能写一个 20 行的小脚本或单测，以后任何人提交代码只要退化直接亮红灯？”*
  * ➔ 落实物理枷锁一，让机器替你记仇。

### 3. 手册自进化的“防臃肿”四大戒律

完善手册是长跑，最忌讳的是把它变成一份又臭又长的杂物堆。请恪守四大戒律：

1. **只记“模式与为什么”，不记“代码片段”**：
   * ❌ 错误做法：在手册里贴 500 行 Vue3 或者 FastAPI 的具体路由实现；
   * ✅ 正确做法：记录“前端状态机 4 态必须显式穷举，空状态与骨架屏优先”的设计模式。
2. **用 ASCII 架构图降维，少写大段空泛文学**：
   * 一张时序交互图、一张前后端分层图，比写五页理论更具穿透力。
3. **设置“实战检验门槛”**：
   * 只有在 **2 个或更多不同项目** 中都被反复验证成功的经验，才升格写入本手册的正文；
   * 仅在单个项目中生效的 trick，留在该项目的 `docs/` 或踩坑记录里，不盲目泛化。
4. **版本化命名与阶段迭代**：
   * 给自己的认知手册打 Tag（如 `v1.0 认知觉醒` ➔ `v2.0 广告实操推演` ➔ `v3.0 多端泛化架构`），每次升级都见证自己认知体系的进化蜕变。
