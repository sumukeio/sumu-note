导入功能方案

## 一、需求背景与目标

- **背景**：用户已经在各种工具或格式中积累了大量内容（txt、Markdown、Word），希望快速迁移到当前笔记系统中，减少复制粘贴成本。
- **目标**：
  - 支持从本地导入 `txt / markdown / word` 文件，并自动生成笔记。
  - 移动端浏览器、PC 端浏览器均可使用。
  - PC 端支持「拖拽文件到页面/文件夹」直接导入。
  - 导入后的笔记在结构、内容保真度和可编辑性之间取得平衡。

## 二、产品目标与原则

- **降低迁移成本**：用户可以一键把旧资料批量带入当前笔记系统。
- **保持内容可编辑**：导入后的内容以可编辑文本为主，尽量减少「只读附件」。
- **操作简单直觉**：
  - 移动端：清晰的「导入」按钮，流程尽量类似微信/网盘的文件上传体验。
  - PC 端：既有按钮上传，也有拖拽区域提示。
- **安全与可控**：给出导入前的预估（文件数量、大小），导入中的进度反馈，导入后的结果说明（成功/失败列表）。

## 三、需求范围与边界

### 3.1 支持的文件类型（首版）

- **txt**：
  - 编码：优先尝试 UTF-8，无法解析时尝试常见编码（如 GBK），若仍失败则提示「编码不支持」。
  - 内容：整文件内容转为纯文本笔记。
- **Markdown（.md）**：
  - 基本语法：标题、列表、引用、粗体、斜体、代码块、分割线等。
  - 图片：首版可以先**不自动导入本地图片文件**，或仅支持网络图片（`![](http...)`）。本地图片路径可保留为原文本。
  - 表格、Task List 等扩展语法：按当前编辑器已有能力渲染；无法完全支持的语法原样保留。
- **Word（.docx）**：
  - 仅支持 `docx`，不支持老格式 `doc`（可在 UI 中明确说明）。
  - 文本内容解析为富文本/Markdown，再落地为本系统笔记格式。
  - 图片：首版可选策略：
    - 方案 A：只导入文本，图片以「[图片略]」/ 占位符+原文件名方式保留。
    - 方案 B：将图片提取为附件上传，并在正文中插入图片链接。
  - 表格：视实现难度，首版可简化为纯文本（例如 Markdown 表格或缩进文本），后续再优化。

> 推荐首版实现时：txt / md 完整支持；docx 以「文本为主，图片简化或占位」的方式快速上线，后续再迭代。

### 3.2 不在首版范围内

- PDF、HTML、PPT、Excel 等其他格式。
- 云端文档直连导入（如 Notion、飞书等）。
- 大批量（上千文件）后台异步迁移工具。

## 四、核心用户场景

- **场景 1：手机端快速导入一篇文档笔记**
  - 用户在微信/QQ/网盘里下载了一个 `.md` 或 `.docx` 文件到手机本地。
  - 打开本应用 H5（或 PWA），进入某个笔记本/文件夹。
  - 点击「导入」按钮 → 系统调用手机文件选择器 → 选中文件。
  - 页面显示「上传中 / 解析中」状态，完成后在当前文件夹下生成一条新笔记。

- **场景 2：PC 端从本地文件夹把旧笔记拖入**
  - 用户在电脑上有一个文件夹，里面放了很多 `.txt / .md / .docx`。
  - 打开 Web 端，定位到某个目标文件夹。
  - 直接把多个文件或整个文件夹拖到页面中指定区域。
  - 系统批量上传并解析，生成多条笔记，每条笔记与原文件一一对应。

- **场景 3：零散补充导入**
  - 用户只偶尔有一两个 txt/md 文件想放入当前项目中。
  - 期望的是：打开当前页面 → 导入 → 选择文件 → 马上看到笔记并可继续编辑。

## 五、交互与信息架构设计

### 5.1 入口设计

- **移动端**：
  - 在文件夹/笔记列表页的顶部工具栏中增加「导入」按钮（图标：向下箭头/文件上传图标 + 文案「导入」）。
  - 也可以在「+ 新建」按钮的下拉中增加「导入文件为笔记」选项（取决于当前整体交互风格）。

- **PC 端**：
  - 顶部工具栏增加「导入」按钮。
  - 中央列表区域支持文件拖拽：
    - 默认状态显示轻量提示文案：「将文件拖拽到此处以导入为笔记（支持 txt / md / docx）」。
    - 拖拽进入时，高亮边框或背景，显示「松开鼠标，开始导入」。

### 5.2 导入流程（按钮上传）

1. 用户点击「导入」按钮。
2. 弹出系统文件选择对话框：
   - 支持多选。
   - 文件类型过滤：`*.txt, *.md, *.docx`。
3. 选择文件后，前端展示导入确认弹窗（可选）：
   - 文件列表（名称 + 大小 + 类型）。
   - 显示预估总大小、文件数。
   - 若有不支持的类型，列表中标红并提示「类型不支持」。
4. 用户点击「开始导入」：
   - 进入进度展示：整体进度 + 单文件进度（可简化为整体进度 + 当前文件名）。
   - 中途可以取消（取消后不再上传剩余文件，已完成的不回滚）。
5. 导入完成后：
   - 在当前文件夹刷新列表，新建笔记排在顶部或按创建时间排序。
   - 显示摘要提示：例如「成功导入 8 个文件，2 个失败」。
   - 可点击「查看详情」查看失败原因（类型不支持、文件损坏、大小超限等）。

### 5.3 导入流程（拖拽）

1. 用户在 PC 将文件/文件夹拖拽到页面指定区域。
2. 页面高亮区域，文案变为「松开鼠标，开始导入 X 个文件」。
3. 松开后，进入与按钮上传相同的「文件列表 + 确认弹窗」，以保持流程一致性。

### 5.4 导入结果与命名规则

- **笔记标题**：
  - 默认：使用原文件名（去掉扩展名）作为笔记标题。
  - 若当前文件夹中已存在同名笔记：
    - 方案 1：自动加后缀「(1)」「(2)」。
    - 方案 2：弹窗询问「覆盖 / 重命名 / 取消」，首版可先用方案 1 降低复杂度。

- **笔记内容**：
  - 按解析结果填充。
  - 在笔记底部可加一行「导入信息」（可选）：
    - 例如：「本笔记由文件导入：原始文件名、导入时间」。

## 六、技术可行性分析

### 6.1 前端实现概览

- **文件选择与上传**：
  - H5 标准：`<input type="file" multiple accept=".txt,.md,.doc,.docx">`。
  - 移动端和 PC 端均可兼容；需在部分浏览器中测试（Safari/iOS、Chrome/Android、Chrome/Edge 桌面）。
  - 拖拽支持：监听 `dragover` / `drop` 事件，阻止默认行为，读取 `DataTransfer.files`。

- **文件大小控制**：
  - 前端在选择后先检查单文件大小与总大小，超出限制直接在前端提示，避免浪费上传带宽。
  - 限制值可配置（例如单文件上限 20MB，总任务上限 200MB）。

- **进度展示**：
  - 使用 `XMLHttpRequest` 或 `fetch + axios` 的上传进度回调实现进度 UI。
  - 也可以按文件为单位，显示「第 n/总数」的简化进度。

### 6.2 后端与解析模块

- **上传接口设计**：
  - `POST /api/import-note`
  - 支持多文件上传（`multipart/form-data`）。
  - 参数：
    - `folderId`：目标文件夹 ID。
    - `files[]`：用户选择的文件列表。
  - 返回：
    - 每个文件的处理结果：`{ fileName, status: success|failed, noteId?, errorMessage? }`。

- **解析管线（建议架构）**：
  1. 接收上传文件，进行基础校验（类型、大小）。
  2. 根据扩展名 / MIME 类型分发到不同的解析器：
     - `txtParser`：主要是编码探测 + 文本读取。
     - `mdParser`：可以直接当作文本，以 Markdown 存储；如系统有 Markdown 支持可直接使用。
     - `docxParser`：
       - 使用成熟库（例如 Node 端 `mammoth`、`docx` 解析库）读取文档结构，转换为 HTML 或 Markdown。
  3. 将解析出的内容转换为系统内部使用的笔记格式（例如 Markdown / 自定义 JSON）。
  4. 写入数据库，生成笔记记录，关联到对应 `folderId`。

- **性能与异步处理**：
  - 对于少量文件（< 20），可以同步处理后一次性返回结果。
  - 对于较大批量，可考虑：
    - 前端拆分为多个请求分批上传。
    - 后端快速返回「已接受」，再通过轮询/通知给出最终结果（后期优化方向，首版可以先不做）。

### 6.3 编码与字符集问题

- 多语言文件可能使用不同编码：
  - 优先以 UTF-8 解码。
  - 如果解码失败，可以尝试通过 BOM 或常见模式（如 GBK）再尝试一次。
  - 仍失败时，在结果中标记为失败，并建议用户转码后重试。

### 6.4 安全与限制

- 防止上传可执行文件 / 恶意脚本：
  - 严格限制扩展名与 MIME 类型。
  - 在解析 Word 文档为文本/Markdown 时，**不执行任何宏或脚本**。
- 上传大小限制与超时处理：
  - 设置合理的 Nginx 或后端上传大小上限。
  - 单请求超时时间控制，避免长时间占用资源。

## 七、产品优化建议与迭代方向

### 7.1 首版可行性与取舍

- **可以上线的最小版本（MVP）**：
  - 支持按钮上传 + 拖拽导入。
  - 支持 txt / md 完整导入。
  - 支持 docx 文本导入，图片用占位符处理。
  - 提供基础结果反馈（成功/失败、失败原因）。
- **暂缓实现的功能**：
  - 文件夹层级自动映射为笔记层级。
  - 后台异步批处理 + 通知。
  - 完整保留 Word 样式（复杂表格、页眉页脚等）。

### 7.2 后续优化方向

- **体验优化**：
  - 导入前的预览功能：随机展示部分内容片段，用户确认无误后再导入。
  - 导入成功后，自动打开第一条新笔记，帮助用户快速检查。
  - 失败文件支持「重新导入」快捷操作。

- **能力扩展**：
  - 支持 PDF（提取纯文本；复杂排版视情况处理）。
  - 支持从压缩包（zip）批量导入。
  - 支持从第三方云文档（如 Notion/飞书）导入，作为单独大功能。

- **结构化导入**：
  - 对于包含多级标题的 Markdown/Word，可尝试自动拆分为多条笔记或多级大纲（需在产品层面设计交互与配置）。

## 八、开发工作量与风险简评

- **前端**：
  - 文件选择 + 拖拽上传 + 进度 UI + 结果显示：中等工作量。
  - 移动端适配需要测试多个主流浏览器。
- **后端**：
  - 上传接口 + 安全校验：中。
  - txt/md 解析：低。
  - docx 解析：中偏高（取决于使用的第三方库与目标保真度）。
- **主要风险点**：
  - Word 文档解析的复杂度（特别是表格、图片、特殊样式）。
  - 编码与特殊字符导致的内容乱码。
  - 大文件/大量文件同时导入时的性能与稳定性。

整体来看，该导入功能 **技术上可行**，首版建议聚焦「txt & md 高质量支持 + docx 文本为主」的路径，先满足 80% 的迁移需求，再在后续迭代中逐步增强样式和多格式支持。
